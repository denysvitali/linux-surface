# SPX SPI-HID startup diagnostic trial L — final scoped result, 2026-09-22

**SPI-HID and IPTSD started successfully on L without startup polling or a
daemon retry.** This is a successful input-enumeration observation; physical
touch/pen operation and reliable startup across repeated boots remain
unverified. Input enumeration, the desktop and the guarded stage-4 audio
baseline passed through **629.82 seconds uptime**. All **283 archived files**
were independently rehashed before this document was finalized. Mainline was
intentionally retained after verification; no recovery return occurred.

An independent read-only review at **200.64–283.46 seconds uptime** confirmed
boot `90f1a5fc-5a70-4bd5-8d7d-99e45039b007`, attempt `20260922l`, release
`7.3.0-rc2-spx-mainline-20260922l+`. L adds bounded, default-off startup
metadata logging to K's SPI-HID code and enables `spi_hid.startup_diag=1` on
this boot. It adds no hardware I/O, reset policy, protocol request or delay;
logging itself may affect timing. This successful boot does not establish
that the intermittent failure seen on J/K is fixed. See
[L preparation](PREPARED-20260922l.md) and
[artifact review](ARTIFACT-REVIEW-20260922l.md).

The early journal contains **64 startup diagnostic lines**: 22 in window 1,
21 in window 2 and 21 in window 3. Each window ends with three headers, one
reset response, one device descriptor, zero polls and zero suppressed lines.
IRQ counts are respectively 3, 4 and 4. No startup timeout, invalid header,
generic error-reset attempt or bounded fallback poll appears. These are
three ordinary power-up sequences inside one boot, not three boot trials or
three failed attempts. Normal reset assertions in those sequences are
distinct from error recovery.

Windows 2 and 3 also log an early IRQ while the software `powered` flag is
false, before their later successful reset-response IRQ. These observations
describe the existing path and do not identify the earlier J/K failure's
cause. The diagnostic records software state, result codes, lengths and report
types; it does not log raw touch report payloads. The reviewed implementation
allows at most four windows of 48 lines each, reserving the last line for a
terminal record and stopping each window at ready/power-down/timeout.

`spi0.0` is bound to `spi_hid`, with module initstate `live`. The loaded
parameter is `startup_diag=Y`, and its sysfs permission is **0444**. The
independently hashed installed module is:

Its vermagic names L, and the GNU build ID exactly matches the note exposed
by the **loaded module** in `/sys/module/spi_hid/notes/`. SPI-HID is absent
from L's initramfs and loads from the installed root module tree. This
establishes that the observed trace came from the intended L binary.

`hidraw4` identifies the SPI `045E:0C21` device. Raw SPI input nodes and both
IPTSD virtual devices are present. `iptsd@dev-hidraw4.service` is active with
PID **764**, `NRestarts=0`, and a successful main-process status. The installed
daemon retry policy was therefore not exercised. This review performed no
input rebind, reload, reset, daemon restart or physical gesture test.
At a further check at **381.58 seconds**, SPI-HID remained ready; bus, logic
and regulator error counters were zero, as was the device-initiated reset
