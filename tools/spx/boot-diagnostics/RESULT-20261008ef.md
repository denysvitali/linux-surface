# EF: demosaiced view of the EV bright frame (C02/C03 evidence, analysis only)

Same capture as `20261008ev`; no boot and no kernel change. The raw 8-MSB view
is grayscale because `camera.py` writes the high bytes of SGRBG10 without
demosaicing.

**Change:** offline conversion of
`/var/lib/spx-boot-diagnostics/functional/20261008ev/camera/frames-bright.raw`
to a 2112x1568 Bayer image (every 5th LSB-pair byte lifted out), demosaiced as
`bayer_grbg8`, then rotated. The original raw is gone with the retired trial
directory; the 8-MSB image survives at `/tmp/spxjpg/bayer8.raw`.

**Observed:** the user looked at the renders and rejected them twice. Looking
at the frame itself: the raw readout is **rotated 90°, not 180°** — only a
quarter turn puts the tabletop horizontal and the chair back upright. The
earlier "a person, a doorway, a ceiling strip" description is not in the
frame, and neither is the green cast. With levels stretched and no colour
correction the frame is **strongly magenta**.

**What was checked, and what was wrong:**

- `orientation = <1>` cannot move pixels. It is read-only metadata
  (`V4L2_CID_CAMERA_ORIENTATION`, flagged read-only in `v4l2-ctrls-defs.c`).
- The mode does program a flip. Intel's ov13858 driver maps `0x3820` bit 4 to
  vertical flip (set = on) and bit 3 to horizontal mirror (clear = on), and a
  2026-09 measurement on this exact part confirms both
  (https://lkml.org/lkml/2026/9/21/1360). `mode_2112x1568_regs` writes `0xab`,
  so both are on, against `0xa8` (neither) in the full-resolution mode. That
  accounts for 180°, not for the 90° the frame shows, so it is not the whole
  answer. The same measurement found the Bayer order does not change with the
  flip, so the pattern is not the variable.
- The "blue at 77% of red" figure came from assigning the planes backwards and
  averaging the whole frame. On the pale wall, with the documented GRBG order
  (first row green, red), the planes read G 42.1 and 41.8, R 36.1, B 31.2.
- A white balance computed from that wall makes the wall grey and turns the
  wood green, so a single gain per plane does not fix the colour. The cause is
  not established.

**Meaning:** the bright frame is genuine scene data, and the earlier "no real
scene" reading was wrong. The camera path is confirmed end to end. Two defects
remain, both unfixed: **the image is rotated 90°**, and **the colour is
magenta with no correction found yet**. `camera.py` still writes an
undemosaiced grayscale preview. No box changes; C01 stays open.
