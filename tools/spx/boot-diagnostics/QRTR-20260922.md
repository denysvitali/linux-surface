# SPX modem startup and QRTR HELLO review — 2026-09-22

The modem failures in trials A and D correlate with failed QRTR service
announcements and a roughly 40-second remote-firmware timeout. A recent
HELLO-handshake change is a concrete candidate for an isolated experiment
after trial E. This is a source-based hypothesis: the captured error messages
do not include the failed send's return code, and no QRTR fix has been tested.

The review changed only this document. Kernel sources, services, modules and
boot selections remain untouched by this review.

## Follow-up: F recurrence and isolated G rollback

E's600-second observation had no modem startup failure. F, with unchanged
QRTR code, failed its first service announcement at29.909858seconds and the
modem crashed at69.894706seconds, approximately40seconds later. It restarted
at70.533028seconds without another announcement failure and remained running
through F's813.84-second observation. See [F's result](RESULT-20260922f.md).
Audio stage1 succeeded separately on ADSP; the modem signature also occurred
before that audio change.

After collecting F, G reverses only commit544d85de4dc2. Both resulting QRTR
files were verified byte-for-byte against the commit's parent. G retains F's
UINPUT, CMAC, audio stage1, A680 fix, DTB and userspace; only its release label
also changes. G is under preparation, not yet a runtime result.

An additional source concern is that `qrtr_bcast_enqueue()` ignores individual
endpoint enqueue failures, so local service registrations during the HELLO
gate can also lose announcements. A general fix must preserve proactive HELLO
and replay the current local service set after handshake completion, handle
concurrent registrations and safely cancel work on disconnect. A simple retry
of one logged NS send is insufficient. G is a diagnostic rollback, not an
upstream-ready solution for passive MHI endpoints; this SPX build uses SMD and
does not enable QRTR_MHI. Observe>=600seconds and seek another clean startup
before treating an intermittent failure as resolved. Keep the planned IPv6
netfilter configuration correction and audio stage2 out of G.

## Candidate source change

Commit `544d85de4dc22c01badfd8cefa59829ce35c4858`,
`net: qrtr: Send HELLO message on endpoint register`, was authored on
2026-08-27 and committed on 2026-09-02. It changes only
`net/qrtr/af_qrtr.c` and `net/qrtr/ns.c`. It adds proactive HELLO transmission
for remote endpoints that wait for the host to initiate communication.

The following locations refer to source HEAD
`907fc689af98a2ae9e7b74d10a74a33f8d4f9e5b`:

- [af_qrtr.c:651](../../../net/qrtr/af_qrtr.c#L651) initializes
  `hello_sent` to false; line 665 schedules the HELLO work asynchronously.
- [af_qrtr.c:594](../../../net/qrtr/af_qrtr.c#L594), `qrtr_hello_work()`,
  retries when the name-server socket or packet allocation is unavailable,
  then sends HELLO through `qrtr_node_enqueue()` at line 622.
- [af_qrtr.c:352](../../../net/qrtr/af_qrtr.c#L352) rejects non-HELLO
  packets with `-EAGAIN` while `hello_sent` is false. Lines 391–392 set the
  flag only after a successful HELLO transmit. Lines 400–401 schedule another
  HELLO attempt when that transmit returns `-EAGAIN`.
- [ns.c:330](../../../net/qrtr/ns.c#L330), `ctrl_cmd_hello()`, now calls
  `announce_servers()` directly. The commit removed its synchronous
  `say_hello()` reply before announcing services.
- [ns.c:228](../../../net/qrtr/ns.c#L228) walks the local servers.
  Any send error other than `-ENODEV` prints the observed announcement error
  and returns immediately. It does not retry the remaining announcements.

A possible ordering is that the modem's HELLO reaches the name server before
the host's queued HELLO completes. The service announcement then encounters
the new `-EAGAIN` gate and aborts. Completing the host's HELLO does not itself
replay the aborted announcement list; another incoming HELLO would be needed
to trigger that path again. This explains the observed correlation if the
remote firmware does not send another HELLO. The existing logs do not prove
that this ordering occurred or identify the modem's internal fatal reason.

## PD-mapper and userspace checks

Kernel `CONFIG_QCOM_PD_MAPPER=m` and userspace `pd-mapper.service` are both
present in D. The SC8180X domain table and relevant kernel service-response
logic are effectively unchanged from the sibling 6.18 source tree.

On the known-good recovery boot
`6394d00d-4cc0-4f01-9239-8de02fa4ae93`, the kernel mapper is bound to all
three remoteproc auxiliary devices and userspace `pd-mapper` is running.
That boot's modem starts at 24.009 seconds without a subsequent fatal in the
reviewed journal. Coexistence therefore does not by itself explain this
mainline regression. A duplicate-mapper experiment remains possible, but has
less direct supporting evidence than the QRTR handshake change.

The installed rmtfs drop-in explicitly orders it after, and requests,
`tqftpserv.service` and `pd-mapper.service`. D satisfies that ordering. It
guarantees service start ordering, not protocol readiness. No service was
stopped, restarted or reconfigured during this review.
