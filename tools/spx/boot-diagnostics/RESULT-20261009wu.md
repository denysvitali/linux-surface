# WU: early clock hold exposes stale speaker compander state

Boot `876ae499-b442-4667-a87e-685390581b38`, kernel
`7.3.0-rc2-spx-mainline-20261004bg+`. One direct WT-to-WU boot, retaining the
candidate configuration and installing the confirmed ASM header correction.
No audio was queued at startup. Baseline collection completed; its network
transfer preceded Wi-Fi association and failed DNS resolution.

**Changed:** loaded `spx_audio_rx_hold` before any PCM opened. Both INT7/8
supplies reported On (forced). Ran the existing microphone reopen test.

**Observed:** the first run stopped before tones because RX7/8_PATH_CFG0
were 0x2 rather than 0, although COMP7/8 controls reported off. The native
setter updates cached state only; early clock power latched compander enable
and retention prevents the later clock event that normally applies bypass.
Playback consumed 5/5 silence buffers. Capture: 403,200 frames, discarded.

With amplifiers parked, cleared only the two compander-enable bits through
the existing codec regmap interface; both clocks remained forced. The same
test then passed its configuration checks, but the first left tone was
absent: 0.473 RMS against 0.342 baseline. DSP consumed 168/168 buffers with
zero fallback. Capture: 760,320 frames, discarded. Peak 1433, minimum PA gain.

**Meaning:** no audible starting point was established, so this does not
settle prevention of reopen failure. It identifies a concrete setup bug:
speaker compander disable must affect hardware while clocks remain on.
The native setter now clears the bypass bit immediately on SPX, including
repeated off settings, and propagates register errors. Build/checkpatch pass;
the driver change still requires hardware validation. Live bit correction
alone did not restore sound after the premature first close.
