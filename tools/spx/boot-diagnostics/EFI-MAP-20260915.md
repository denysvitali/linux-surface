# SPX GRUB EFI memory-map observation, 2026-09-15

## Procedure and reboot hygiene

Immediately before the authorized known-good reboot:

- boot start: `2026-09-14 17:41:56`
- boot ID: `40bc7e68-538d-4c15-a39d-84158efe9e6a`
- kernel: `6.18.3-1-surface+`
- command line marker: `spx_boot=known-good`
- GRUB: `saved_entry=spx-known-good`, empty `next_entry`

The GRUB menu remained visible for five seconds. At its console the user ran
`lsefimmap`, photographed the displayed map, exited the console and allowed the
unchanged known-good entry to boot. No register read or write was attempted.

The resulting boot started at `2026-09-15 20:03:08` with boot ID
`5c7a0beb-3fb6-4086-9e72-a34102c8119a`. It again runs
`6.18.3-1-surface+` with `spx_boot=known-good`; the persistent GRUB default is
unchanged and `next_entry` remains empty.

## Result

The photographed EFI memory map has no descriptor whose physical range covers
`0x17c10000`, the APSS watchdog base. Stage 0a therefore failed closed. The
stage-0b `read_dword` probe is not permitted on this evidence because an
unmapped access may fault GRUB and require a manual power cycle.

The original photograph is preserved outside the repository at
`/var/lib/spx-boot-diagnostics/efi-map-stage0a-20260915/lsefimmap.jpg`:

- size: 291252 bytes
- sha256: `dd83184adfe472ec9e5ad5c3971d2d5bdd46c593b84d58449679df3c3e0fbb6d`

The control boot through `.dtb.wsa` has neither
`/proc/device-tree/soc@0/watchdog@17c10000` nor `/dev/watchdog0`. This is
consistent with the deployed DTB and distinguishes it from the preceding boot,
whose live tree matched `.dtb.wdt` and whose hardware watchdog was owned by
systemd.

## Consequence

The experimental boot lock remains in force. A different documented
bootloader mapping mechanism, or an independent external reset controller that
can recover the device from a GRUB/EFI fault, is required before register
access and forced-expiry validation can proceed. Mainline device-component
testing remains pending behind that requirement.
