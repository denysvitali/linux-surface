# Trial 20261008ez: rear only in the DT (front and IR disabled)

Trial boot `b783ce39`, kernel `7.3.0-rc2-spx-mainline-20261004bg+`. Return to
known-good at 900 s (`trial.py return` at my request): boot `039a2f9d`,
`6.18.3-1-surface+`, persistent default `spx-known-good`, next entry empty,
known-good payloads intact.

**Changed:** `camera@36` (front) and `camera@60` (IR) set to `status = "disabled"`
(commits `7610be8a0268`, `7b7debc4f402`). Otherwise the ey DTB.

**Observed (live, trial kernel):**
- Rear OV13858 at `4-0010` is bound to the `ov13858` driver. It logs nothing on
  a successful probe, which explains the silent rear in ew/ex/ey.
- The media graph registers `ov13858 4-0010` with one source pad and **0 links**.
  `msm_csiphy2` has no link to it. Front and IR are not in the graph.
- camss binds and logs its CSIPHY profiles; no error is printed.

**Meaning:** the rear probes correctly; camss never creates its links. In
`drivers/media/platform/qcom/camss/camss.c`, `camss_parse_ports()` queues an
async subdev for every CSIPHY endpoint that has a remote, and does not check
whether that remote is enabled. Links are created only in
`camss_subdev_notifier_complete()`, which runs only when every queued subdev is
bound. Disabling a sensor leaves its CSIPHY0 (front) and CSIPHY3 (IR) endpoints
pending, so no link is ever made.

**Correction:** the ey result (`RESULT-20261008ey.md`) concluded that the front
failure does not block the rear. That was wrong: the test left the CSIPHY0 and
CSIPHY3 endpoints dangling. Disabling a node is not a valid way to isolate a
sensor. The front bus-1 failure gates every link in the graph, which fits ew and
ex (the rear never linked there either).

**Next:** remove the front's CSIPHY0 endpoint (keep the front node disabled)
and keep IR enabled. Expect the rear and IR to link. This tests the mechanism.
